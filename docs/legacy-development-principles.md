# RN Handover — 工作指引

適用於本 repository 的網站維護、程式修改、問題調查、規格整理、測試及部署。

本指引規定工作方法；具體功能規則、例子及驗收要求保存於相關規格、issues 和測試。兩者須配合使用，不能以通用指引代替功能要求。

## 1. 開始任務：讀取相關紀錄

每次開始任務時：

1. 讀取本指引、README、相關功能規格、現有程式及測試。
2. 按任務搜尋相關 GitHub issues，包括 open 和 closed。
3. 同時使用功能標籤及關鍵字搜尋，避免漏掉未加標籤的歷史紀錄。
4. 讀取相關 issue 內容及討論，不只讀標題。
5. 分清已確認要求、待審方案、歷史回報、已重現問題及已驗證結果。

Issue 已建立、已關閉，或曾有 assistant 表示「完成」，均不能單獨作為功能正確的證明。

如無法讀取相關紀錄，明確交代缺少的資料及其影響，不得聲稱已完成查閱。可獨立進行的工作繼續處理，不因不相關的資料缺失停止整個任務。

只需深入閱讀與任務及其影響範圍相關的內容，不要求每次重新閱讀所有歷史 issues。

## 2. 修改範圍與原有行為

每次修改前，確認：

- 今次目標及完成條件。
- 相關已確認規則。
- 必須保留的原有行為。
- 驗收例子及已知例外。
- 本次不涉及的功能。
- 尚未解決的矛盾或證據限制。

已確認的規則持續有效，不要求使用者每次重述。使用者要求修改其中一項，不代表授權重設其他設定。

新例子與原有規則矛盾時，先指出具體矛盾，查核原文、規格、相關 issues 及測試；不可直接以最新一句覆蓋整套規則。

能依現有證據解決的問題先自行查證。只有仍無法判定，而且會改變實際行為或驗收答案時，才向使用者釐清。

一般例子應抽取適用條件，不可硬編成特定居民、房號或疾病關鍵字。亦不可將只適用某類事件的例外擴大成所有功能的通則。

使用者要求討論或草擬時，先提供可審閱結果；未授權實作前，不修改程式或部署。已獲授權的實作則完成必要修改及驗證，不反覆要求相同確認。

### 草稿詳盡程度與 Review 分工｜暫行

草稿可以詳盡，不設硬性篇幅限制，也不強制所有草稿採用同一格式；以結構清楚、避免無意義重複及保留必要內容為準。

開首先交代結論、修改重點及需要使用者決定的事項，後面保留完整理由、相關既有行為、規則、例外、驗收例子、回歸風險、證據限制及未解決問題。摘要不能取代完整修改方案；不得以「優化」或「簡化」為由，擅自刪減已確認內容。

使用者通常主要審閱方向及重點，不預期逐字校對。AI 仍須負責查核來源、準確性、前後一致及完整性；使用者同意草稿方向，不等於逐項核實其中所有事實，不得因此將未核實內容標示為「本人確認」。

重要歧義或需要使用者決定的取捨，應明確指出；其餘按既有授權及規則完成，不將例行查核責任交回使用者。

此為暫行原則，按實際使用結果調整。

## 3. 規格、例子與錯誤紀錄的完整保存

各類內容的用途如下：

- AGENTS.md：通用工作流程及必須遵守的做法。
- 功能規格：目前已確認的行為、適用條件及例外。
- Issues：歷史問題、證據、原因、方案、進度及驗收要求。
- 測試：以可執行案例驗證具體行為。
- Git commit／部署紀錄：保存實際修改及交付版本。

同一要求如在多處被引用，須指出主要保存位置，避免維護互相矛盾的副本。

整理、精簡或重組內容時，逐項對照原有要求與新的保存位置。不得遺失功能、限制、例子、例外、來源或驗收條件。

合併重複文字時，保留其中不同的適用條件及含義。移動或合併要求後，列明對應位置，不以「已涵蓋」代替實際核對。

使用者已確認的例子應持續保存；取代舊要求時，明確記錄哪項被取代及原因，避免舊規則日後重新被套用。

## 4. GitHub 與 Sites 來源核對、同步及發布

### 4.1 首次整合前

GitHub 與 Sites 目前不能假設已完全同步。

每次實作前，核對兩邊實際來源、commit 及部署版本。若有差異：

1. 比較程式、規格、測試及部署設定。
2. 列出有效更新、舊內容及待確認衝突。
3. 保留兩邊已有的有效修改。
4. 不以其中一邊的舊版本直接覆蓋另一邊。
5. 保存整合結果及來源對照。

首次整合完成前，不聲稱已有單一程式來源。

### 4.2 整合完成後

以 GitHub 作為主要程式及規則紀錄。

除使用者另有指示外，每次已授權的網站交付，應一併完成：

1. 對本次來源執行必要檢查及 build。
2. 保存並推送對應 GitHub 修改。
3. 經支援的 Sites 流程發布同一份已驗證來源。
4. 在相關 issue 記錄 GitHub commit、Sites source commit、部署版本及驗證結果。

兩邊 commit SHA 可以不同，但必須能證明應用程式內容對應，並列明必要的 hosting 設定差異。

若驗證後再次改動來源，執行受影響的檢查及重新 build；不得部署與已驗證內容不同的產物。

### 4.3 同步或發布失敗

明確指出：

- GitHub 哪個版本已保存。
- Sites 哪個版本已保存或部署。
- 測試、build 或部署停在哪一步。
- 網站目前仍使用哪個已確認版本。
- 剩餘工作及已知影響。

不得將 GitHub 已保存等同網站已部署；亦不得將一次最新來源同步描述為已補回全部歷史。

未實際建立及驗證自動部署前，不聲稱 push／merge 後會自動更新網站。由 agent 執行完整流程與無人值守自動化是不同安排。

## 5. 來源、日期與事件狀態

保留原始紀錄及來源連結，讓摘要、狀態和任務可追查。

處理紀錄時，分清：

- 事件主體。
- 事件日期。
- 紀錄日期。
- 到期日期。
- 報表／shift 日期。

相對時間按原文的時間基準計算，重新上傳或分析不應延後期限。不要將 note 時間直接當成動作截止時間，也不要憑模糊文字捏造精確日期。

同一來源可以支援多個分類。不得因加入 Leave、Appointments 或 Follow-up，而遺漏相關 Health 事件。

解析、摘要、分類或去重不得令重要事件、未來預約或不同後續動作消失。原始 note 較舊，不代表其中的未來安排已失效。

分清「要求執行」「已有完成證據」「等待回覆」及「未能確認」。

未見完成紀錄，不等於確定未做；較新的 note 亦不自動推翻另一事件的狀態。事件主體不同、時間不同或內容無關時，不得互相覆蓋。

有矛盾或資料不足時，保留相關來源並標示需核對，不將推測呈現為確定事實。

具體日期計算、Leave 狀態及預約規則，依相應功能規格與 issues 執行。

## 6. Follow-up 與已處理項目

Follow-up 表達具體、有來源支持的下一個 RN 動作，不將整段病歷轉成永遠未完成的提醒。

按下一個動作判斷時間及分類。同一事件可以有不同步驟、負責人和期限，不應將整件事一律推遲或一律視為今日工作。

完成條件必須對應該步驟。例如：

- 「已加入 GP list」不等於「GP 已 review」。
- 「已聯絡」不等於「已收到回覆」。
- 「RN to add」不等於「已加入」。

流程預設不得冒充來源已證實的事實；明確記載的其他負責人或跟進安排優先。

Tick 只表示當前具體步驟已處理，不代表整個事件永久結案。

Tick 後：

- 淡化保留項目、原文、來源、日期及狀態。
- 允許搜尋、查看、找回及取消 tick。
- 取消 tick 後恢復相應待辦狀態。
- 自動 tick 必須有明確完成證據。

新結果、新指示或情況改變，不得被舊 tick 隱藏。合併重複內容時，保留不同動作、不同期限及來源；同時避免為同一動作重複生成任務。

詳細時間分類、pathology 流程及例外依 issue #3 及其後確認的功能規格執行。

## 7. 修正、回歸測試與預期答案

先理解問題發生在哪一層：資料解析、事件辨識、規則計算、分類、狀態、API 分析或畫面呈現。未定位前，不以重寫整個功能作為預設修法。

修正問題時加入能重現該問題的合成案例，並執行受影響的既有測試。不可只驗證新功能而忽略已確認的相關行為。

使用者確認的例子是驗收依據，不是為配合現有實作而隨意調整的測試答案。

測試預期答案如需修改，必須明確說明：

1. 原答案錯在哪裏。
2. 正確規則及來源。
3. 對應 issue 或使用者確認。
4. 修改對其他案例的影響。

不得為令測試通過而修改答案、刪除失敗案例或降低驗證要求。

完成前檢查程式、規則及測試的 diff，特別留意：

- 原有判斷或例外是否被移除。
- 日期邊界及狀態重設是否改變。
- 測試預期答案是否改動。
- 是否有無關功能被修改。
- 去重、篩選或 tick 是否令資料消失。

程式修改依 repository 當前文件及 CI 設定執行標準檢查，包括 typecheck、測試及 production build。若設定已改，先核對現行命令。

必要檢查通過後，不無限重跑相同檢查；有新修改、失敗或未解決風險時，再追加相應驗證。


若問題涉及匯入文件、事件日期或來源歸屬，驗收必須包含來源解析至狀態／顯示的連接，不可只向判斷函數提供已整理好的 notes。使用合成文件版面案例檢查換行、跨頁、居民邊界及原文保留；事件日期與紀錄日期分開驗證。

對「無資料／無事件／有衝突」的預設及例外，逐項核對是否有來源支持及實際介面影響。測試通過不能證明例外本身合理；若因已確認規則修正預期答案，保留原案例並記錄理由與對應 issue。

固定計算由程式執行。額外 AI／API review 可以提供參考，但不代替已確認規則、合成案例、來源比較及測試。

## 8. 驗證與交付聲明

分開報告以下驗證狀態：

- 資料解析與來源對應。
- 規則及日期計算。
- 事件分類與狀態。
- API 分析。
- 畫面與實際操作。
- Production build。
- 部署結果。

每項聲稱須有相應證據；未做的標示未驗證或不適用，不用籠統的「全部測試通過」掩蓋範圍。

Build 成功不代表畫面正確；部署成功不代表分析結果正確；mocked API 測試不代表真實 API 已測試。

畫面、API 或其他驗證受環境限制時，說明限制及已完成部分，不虛構成功，也不將未驗證直接說成失敗。

交付時提供足以判斷結果的資訊：

- 實際改了甚麼及原因。
- 保留了哪些相關原有行為。
- 驗證方法及結果。
- 是否改動測試預期答案及原因。
- GitHub／Sites 版本對照。
- 未完成或未驗證部分。

文件或 issue 更新完成，不代表對應功能已修好。

## 9. 居民資料、存取能力與臨床草稿

分清：

1. 讀取或修改網站程式。
2. 網站執行 API 分析。
3. 取得使用者瀏覽器內最新居民資料。

讀到網站程式，不代表讀到使用者瀏覽器內的居民資料。Upload／分析成功，也不代表對話中的 assistant 已取得分析結果。

沒有實際讀取最新資料時，不得聲稱已核對最新 handover；亦不得以舊資料冒充最新來源。

使用匯出檔或其他資料時，確認其資料日期及版本，不根據網站部署版本推斷居民資料是否最新。

撰寫臨床 note 時，分清已讀來源、使用者新增資料及未確認細節，不自行加入給藥途徑、藥效、時間含義或其他臨床事實。

準確說明本機保存、API 處理、匯出及備份的實際方式；本機保存不等於資料從未傳送作分析。

不為方便 assistant 存取而擅自改成雲端保存居民資料。資料架構改變須獨立討論及授權。

程式庫及驗收測試只使用合成資料。不得提交居民紀錄、原始報告、私人 browser backup、私人匯出檔、API keys 或其他憑證。

## 10. Issue 狀態、更新與結案

每個問題分清：

- 歷史回報。
- 已在指定版本重現。
- 原因已核實。
- 已實作修正。
- 已通過指定驗收。
- 已部署。
- 尚未完成或未驗證。

歷史回報未經現版本重現，不直接標示為現存 bug。曾聲稱修好但缺乏驗證證據，亦不直接標示為已驗證。

原因尚未確定時，保留假設及證據限制；不得將未比較的 GitHub／Sites 版本或未查明的 commit 寫成已核實歷史。

在相關 issue 記錄：

- 所用來源及版本。
- 重現案例或步驟。
- 已確認規則。
- 修改內容及相關 commit。
- 驗收結果與部署版本。
- 未解決事項及限制。

達到該 issue 的驗收條件後才結案。已關閉 issue 仍保留作後續任務查閱。

新發現且不屬於當前範圍的獨立問題另開 issue，連結相關紀錄，不將所有問題塞入同一項任務。若直接阻礙當前目標，說明其依賴關係並處理必要部分。

## 11. 六個 Issues 的任務入口

| Issue | 功能／工作範圍 | 修改時須重點核對 |
| --- | --- | --- |
| #1 | BNO 計算及今日 opening 重設 | U／BO、opened 當日、今日規則、閾值、日期案例、證據限制 |
| #2 | 修改保護、版本同步及交付證據 | 原有行為、測試答案差異、GitHub／Sites 對照、驗證聲明 |
| #3 | Follow-up 時間、下一步及 tick 保留 | 原紀錄時間基準、具體完成點、淡化找回、新任務、去重 |
| #4 | Leave 主體及離院／返院狀態 | 居民與家屬區分、相關事件證據、灰色顯示、未知狀態 |
| #5 | 來源與分類完整性 | 解析完整性、多分類、Health、未來 appointment、原文追查 |
| #6 | 資料位置及存取能力 | 最新資料來源、本機／API 路徑、匯出、能力說明 |

以上為入口，不代替閱讀相關 issue 本文及討論。未來新增功能或 issue 時，更新索引並保留既有連結。

以功能標籤及工作類型／狀態分類 issues；搜尋時同時使用關鍵字。歷史回報標籤不代表已重現，awaiting-review 亦須與實際審閱狀態一致。
